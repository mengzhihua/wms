# WMS 技术方案

WMS 是仓储执行系统。收货、上架、分配、拣货、发运和库内作业以本系统账为准。IR 只拉出库和库存快照，并下发分配或补货。

## 1. 运行位置

| 场景 | 后端 | 说明 |
| --- | --- | --- |
| 单机 | `8080` | `application.yml` |
| 发行包 | `8083` | `scripts/package-native.sh`，与 IR `data.sql` 的 `base_url` 一致 |
| 源码直接启动 | `8080` | `application.yml`。同机联调发行包时用 `8083` |

开放接口前缀 `/api/open/` 使用 `X-Api-Key`（`wms.open.api-key`，控制塔种子为 `wms-open-key`）。其余接口要登录 Bearer。演示账号 `admin / admin123`。

仓号：控制塔使用 `WH-SH` / `WH-BJ` / `WH-GZ`，落到本系统时映成 `WH01` / `WH02` / `WH03`。

## 2. 主链路

```text
ASN 收货 → 上架
出库单 → 分配 → 拣货 → 复核打包 → 发运
拣货位低于 minStock → 仓内补货，或从另一仓调拨
```

## 3. 控制塔读

`GET /api/open/ir/snapshots`：

| 块 | 内容 |
| --- | --- |
| `outbound` | 出库单号、外部单号、仓、状态、首行 SKU |
| `inventory` | 按仓、货主、SKU 汇总的可用量 |

## 4. 控制塔写

`POST /api/open/ir/actions` 失败且结果可判定时，控制塔回退专用口。

| 指令 | 专用口 | 作用 |
| --- | --- | --- |
| `WMS_ALLOCATE` | `POST /api/open/ir/allocate` | 按出库单号或外部单号分配 |
| `WMS_REPLENISH` | `POST /api/open/ir/replenish` | 带 `fromWarehouseCode` 且与目标仓不同时跨仓调拨；否则按仓 / SKU 做 Min/Max 补货 |

没有 API Key 时，控制塔登录后：

- 分配：按单号查出库单 id，`POST /api/outbound/order/{id}/allocate`
- 跨仓补货：`POST /api/inventory/replenish/transfer`（源仓、目标仓、SKU、数量、货主）。库存先落到目标仓收货暂存位，任务为 `IN_TRANSIT`，确认后才进拣货位。源仓与目标仓相同则退回仓内 `generate`
- 开放出库创建成功后，`wms.bms.mode=http` 时按件数把出库操作费推到 BMS。仓号仍用 WMS 的 `WH01` 这一类编码。默认 mock，不外呼。
- 采购入库收完后，`wms.srm.mode=http` 时把累计收货数量推到 SRM `POST /api/integration/wms/receipt`。退货和未收完的单据不推。默认 mock，不外呼。
- 同仓补货：`POST /api/inventory/replenish/generate`

非空幂等键按 `type|业务键|key` 缓存。

OMS 关闭模拟后走另一组开放口，同样要 `X-Api-Key`：`POST /api/open/outbound`、`/outbound/cancel`、`/return`。外部单号重复推送返回已有单据。仓号 `WH-SH`、`WH-BJ`、`WH-GZ` 落到 `WH01`、`WH02`、`WH03`。物料必须已在对应货主下存在。

## 5. 边界

调拨扣源仓可用量，加到目标仓拣货位，任务直接完成。它不替代手工移库和盘点。控制塔不直接改库存流水。
